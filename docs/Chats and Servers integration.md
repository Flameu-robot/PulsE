# Концептуальная архитектура: "Unified Group Entity" (UGE)

## 1. Фундаментальная идея

В основу системы положен принцип **"Эластичной Сущности"**. Мы отказываемся от разделения на "Чаты", "Каналы" и "Сервера" как от разных, независимых сущностей.

Вместо этого вводится единая сущность — **Группа (Group)**.

- В базовом состоянии Группа представляет собой текстовый чат или канал (аналог Telegram).
- При активации дополнительных модулей Группа расширяет свой функционал, превращаясь в полноценный голосовой сервер (аналог Discord).

**Ключевое преимущество:** Плавная масштабируемость функционала без миграции данных и смены контекста для пользователя.

---

## 2. Распределение ответственности (Service Topology)

Система строится вокруг двух основных микросервисов, взаимодействующих через событийную модель (Event-Driven).

### A. Messaging Service (Хранитель контекста)

Отвечает за "базовый слой" существования Группы.

- **Владелец данных:** Таблица `groups` (или `communities`).
- **Функции:**
    - Хранение метаданных группы (Название, Аватар, Владелец).
    - Управление списком участников и их базовыми правами.
    - Хранение и доставка текстовых сообщений.
    - Управление настройками (Feature Flags) — определение, во что "превращается" группа (в простой чат или в голосовой хаб).

### B. Space Service (Модуль расширения)

Отвечает за "надстройку" реального времени.

- **Владелец данных:** Таблица `voice_rooms` (привязана к Группам).
- **Функции:**
    - Управление голосовыми сессиями (WebRTC Signaling).
    - Прием и маршрутизация медиа-потоков (Voice, Video, Screen Share).
    - Управление состоянием "Кто говорит", "Кто стримит".
    - Существует только там, где это разрешено настройками Messaging Service.

## 3. Модель данных (Database Schema)

### Messaging Service DB

#### Таблица: `groups`

Единая таблица для всех типов сообществ.

|Поле|Тип|Описание|
|---|---|---|
|**id**|`BIGSERIAL`|PK. Глобальный идентификатор группы.|
|**name**|`VARCHAR`|Название.|
|**type**|`ENUM`|`PERSONAL`, `CHANNEL`, `GROUP`.|
|**features**|`JSONB`|**Ключевое поле.** Массив активных возможностей.  <br>Пример: `{"voice": true, "video": true, "screen_share": true}`.|
|**owner_id**|`BIGINT`|ID создателя.|

#### Таблица: `messages`

Стандартная таблица для хранения переписки, привязанная к `group_id`.

---

### Space Service DB

#### Таблица: `voice_rooms`

Хранит структуру голосовых каналов внутри Группы. Создается только при активации голосового модуля.

|Поле|Тип|Описание|
|---|---|---|
|**id**|`BIGSERIAL`|PK.|
|**group_id**|`BIGINT`|FK на таблицу `groups` (Messaging Service).|
|**name**|`VARCHAR`|Название комнаты (например, "General").|
|**status**|`ENUM`|`ACTIVE`, `EMPTY`.|

#### Таблица: `voice_sessions`

Динамическая таблица "кто где находится" (in-memory cache / DB).

|Поле|Тип|Описание|
|---|---|---|
|**room_id**|`BIGINT`|FK на `voice_rooms`.|
|**user_id**|`BIGINT`|ID пользователя.|
|**stream_type**|`ENUM`|`AUDIO`, `VIDEO`, `SCREEN`.|

## 4. Жизненный цикл взаимодействия (Workflow)

### Сценарий 1: Активация "Discord-режима"

1. **Frontend:** Пользователь (Владелец) в настройках Группы включает переключатель "Голосовые каналы".
2. **Messaging Service:** Обновляет поле `features` в таблице `groups` -> `voice: true`.
3. **Event Bus (Kafka):** Сервис публикует событие `GroupFeatureUpdated`.
4. **Space Service:** Подписывается на событие.
    - При получении события проверяет, есть ли уже голосовые комнаты для этой `group_id`.
    - Если нет — создает дефолтную структуру комнат в таблице `voice_rooms`.
5. **Result:** Группа остается прежней сущностью в БД, но получает новый функционал.

### Сценарий 2: Вход в голосовой канал

1. **Frontend:** Пользователь кликает на голосовую комнату в списке.
2. **Frontend -> Space Service:** Отправляет запрос `ConnectToRoom` через WebSocket.
3. **Space Service:**
    - Проверяет у себя наличие комнаты.
    - (Опционально) Запрашивает у Messaging Service подтверждение прав пользователя (кэшируется).
    - Генерирует WebRTC Offer / SDP конфигурацию.
4. **Frontend:** Получает конфиг, устанавливает P2P соединение через Media Server.
5. **UI Update:** Frontend отображает пользователя в списке "Говорящих".
